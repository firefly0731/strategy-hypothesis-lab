# Phase 0 보고서: 신호 일치성 검증

- 작성일: 2026-11-20
- 브랜치: `feat/live-momentum`
- 데이터: data.binance.vision 1분봉과 펀딩비, 2021-01-01 ~ 2026-11-18 UTC. 11-19 일간 아카이브는 아직 공개되지 않았다.
- 범위: 주문을 내지 않는 오프라인 검증만 했다. 거래소 접속이나 API 키는 쓰지 않았다.

## 결론
아래 기준을 모두 통과했다. 실거래 경로의 신호, 진입·청산, 사이징 배율이 백테스트와 일치한다.

| 검증 | 대상 | 결과 |
|---|---|---|
| 판단 시각별 신호 (p, UB, LB, VWAP, σ) | 실데이터 최근 250세션 × 3종목 = 9,000회 판단 | 일치. 부동소수점 반올림 차이만 있다(rtol 1e-12) |
| 진입·청산 (방향, 시각, 가격, maker 여부, 청산 사유, 판단 번호, 진입 종류) | 같은 범위, 거래 371건 | **완전히 일치(0건 차이)** |
| 시장가 fallback 경로 | 진입 23건, 청산 14건 (실데이터) | 일치 |
| 사이징 배율 (펀딩 포함) | 실데이터 최근 60세션 | 세션 수익률 Σ 배율 × 단위수익률 = `build_portfolio` + `drawdown_throttle` (rtol 1e-9) |
| look-ahead 교란 | 합성 데이터에서 T 이후 봉 전부 교란 | T 이전에 결정된 신호와 거래가 비트 단위로 동일 |
| 개장 시점에서 자른 데이터 | 실데이터 마지막 세션, 합성 데이터 2세션 | 전체 데이터와 사이징 배율이 동일 |

실데이터 250세션 안에는 전환(flip)이 한 번도 없었다. 그래서 전환, 비용 필터, 장애 봉 필터 경로는 그 상황을 일부러 만든 합성 데이터로 검증했다. 테스트는 연구 19개, 실거래 48개로 모두 통과했다.

## 구현 방식
- **신호**: 연구 코드 `build_sessions`와 `compute_signals`를 그대로 재사용한다.
  - 판단 시각 `now`에 마감된 봉만 넣고, 세션의 나머지는 NaN으로 채운다.
  - `now` 이후 데이터는 입력 단계에서 잘라낸다.
  - 직전 봉이 없으면 `DataGap` 예외를 내고 판단하지 않는다.
- **집행**: `MakerChaseExecutor`를 새로 구현했다. 분 단위 이벤트로 도는 상태 기계다.
  - 처리 순서는 maker 체결 → 시한 초과 시 시장가 → 전환 후속 진입 → 판단 → 마감 청산이다.
  - 거래소 연결부는 교체할 수 있다. 지금은 백테스트 체결 규칙(가격 관통)을 쓰는 `SimBarVenue`다.
  - Phase 1에서는 실제 호가와 체결 데이터 기반 모의 연결로, Phase 2에서는 Binance 연결로 바꾼다.
- **사이징**: `session_sizing(data, day)`는 `day` 이전 세션만 써서 배율 scale, 종목별 실효 레버리지, 낙폭 배율 g를 계산한다.
- **설정**: 기본값은 `dry_run=true`, `mode=replay`다. 실주문은 아래가 모두 맞아야 켜진다.
  - mode가 testnet 또는 live
  - `dry_run=false` (불리언)
  - 설정 검증 통과
  - 만료일이 있는 승인 토큰 `LIVE_MOMENTUM_ACK=phase2-testnet:YYYY-MM-DD`
  - API 키는 환경변수나 권한 600인 파일에서만 읽고, 출력하지 않는다.

## 리뷰에서 발견해 고친 문제
별도 리뷰어 에이전트가 검토했다.

| 심각도 | 문제 | 조치 |
|---|---|---|
| 중 | 비교 기준 백테스트가 `sizing="vol"`이었다. 이 모드는 14세션 종가 변동성이 없으면 세션 자체를 건너뛴다. 채택 파이프라인(`unit_trades`)은 `fixed`다. 합성 데이터 워밍업 구간에서 실거래 경로는 2건을 거래했고 백테스트는 0건이었다. 비교를 16번째 세션부터 시작하고 있어서 이 차이가 가려졌다 | `backtest_config`의 기본값을 `fixed`로 바꿨다. 워밍업을 포함한 전 세션을 비교한다. 이를 확인하는 테스트도 추가했다 |
| 중 | 사이징 테스트가 모두 펀딩을 끈 상태였다 | 펀딩을 켠 실데이터 검증과 합성 펀딩 검증을 추가했다 |
| 중 | 다음 경우에 주문이 켜질 수 있었다: TOML에서 `dry_run = 0`, `sends_orders`가 검증을 건너뜀, 승인 토큰에 만료가 없음 | 불리언 타입을 검사한다. 주문 여부를 판단할 때 매번 검증한다. 승인 토큰에 만료일을 넣었다(최대 31일) |
| 중 | 키 파일 형식이 틀리면 조용히 환경변수 키로 넘어갔다 | `secrets_file`을 지정하면 그 파일만 읽는다. 키가 없으면 오류를 낸다 |
| 하 | 마감 청산이 마지막 판단보다 먼저 시작되는 설정을 막지 않았다. g 계산에서 고점을 정하는 방식이 연구 코드와 조금 달랐다 | 설정 검증을 추가했다. g는 `drawdown_throttle`이 그 세션에 주는 값을 그대로 쓴다 |
| 테스트 공백 | 장애 봉, 비용 필터, 3배 상한, 낙폭 축소가 실제로 작동하는 경우를 검증하지 않았다 | 각각을 검증하는 테스트를 추가했다 |

## 운용 전에 결정이 필요한 사항

### 1. 낙폭 축소 계산을 어느 이력에서 시작할지 (사이징에 직접 영향)
낙폭 축소는 경로에 의존하므로, 계산을 언제부터 시작하느냐에 따라 현재 배율이 달라진다. 2026-11-18 마감 기준(펀딩 포함):

| 시작점 | DD | g | 고점 |
|---|---|---|---|
| 2021-01 (run_sizing, walk-forward와 같음) **← 현재 구현** | 10.29% | 0.31 | 2025-12-15 |
| 2026-01 | 9.11% | 0.39 | 2026-03-02 |
| 8개월 (`daily_report.py` 기본값) | 6.79% | 0.55 | 2026-04-15 |

연구 코드 안에서도 `daily_report.py`가 다른 시작점을 쓴다. 현재 구현은 검증된 walk-forward 성과와 같은 2021-01을 기준으로 한다.
- 이대로 운용하면 지금은 노출이 정상 대비 약 1/3이다. 낙폭이 줄어야 배율이 회복된다.
- 실계좌 손익으로 낙폭을 계산할지(실거래 시작 후)도 함께 정해야 한다. 그렇게 하면 백테스트와 1:1이라는 조건에서는 벗어난다.

### 2. 최근 성과
- 최근 60세션: 낙폭 축소 적용 −0.19%, 미적용 +0.89%
- 2026년 1월~11월 18일: 낙폭 축소 적용 −4.30%

기대 성과 문서의 "2026년 약세"와 같은 흐름이다.

### 3. 데이터 지연
- 일간 아카이브는 하루 정도 늦게 공개된다. 실시간 운용에서는 REST(`/fapi/v1/klines`)와 WebSocket으로 직접 받은 봉을 써야 한다.
- 받은 봉이 아카이브와 같은지는 Phase 1에서 매일 대조한다.
- 2026-11 펀딩비 월간 아카이브가 없어서 연구 코드에서는 0으로 처리됐다. 실시간 운용에서는 REST `/fapi/v1/fundingRate`로 받는다.

### 4. 틱 크기
틱 크기는 연구 코드에 하드코딩돼 있다(BTC 0.1, ETH/SOL 0.01). Phase 1 시작 시 `exchangeInfo`로 확인한다.

## 알려진 한계 (백테스트와 같음, 실거래로 검증할 대상)
- maker 체결은 1분봉에서 가격이 지정가를 관통했는지만 본다. 대기열 위치나 부분 체결은 모델링하지 않았다. Phase 1의 핵심 측정 항목이다.
- 손절은 30분 판단 시각에만 확인한다.
- 실거래 경로에서도 maker 청산이 체결되면 후속 진입은 다음 분 경계에 낸다. 백테스트와 같게 하려고 일부러 그렇게 했다.

## Phase 1 계획 (승인 필요)
- 주문 없이 2~4주 운용한다. 서버는 AWS 도쿄이고 chrony로 시계를 맞춘다.
- 실시간 1분봉, 체결, 호가 데이터를 받아 위 상태 기계로 가상 주문을 낸다.
- 체결은 두 가지 기준으로 모의한다. 하나는 1분봉 가격 관통(백테스트 규칙)이고, 다른 하나는 실제 체결 데이터의 지정가 관통이다.
- 매일 리포트에 넣을 항목:
  - 신호, 가상 체결, 손익, maker 체결률
  - 같은 날을 아카이브 데이터로 백테스트한 결과와의 차이
  - 수신한 봉과 아카이브의 차이
- 이번에 함께 구현할 것:
  - 리스크 한도: 일일 손실, 종목별 명목금액, 총 레버리지, 데이터 지연
  - 킬 스위치
  - 상태 저장과 재시작 후 대조
  - 로그
  - systemd 유닛
