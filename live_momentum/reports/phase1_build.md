# Phase 1 보고서: 모의 운용 시스템 구축

- 작성일: 2026-11-21
- 브랜치: `feat/live-momentum`
- 범위: 주문 없는 모의 운용 시스템의 구현과 오프라인 검증까지. 서버 배포와 실제 운용은 아직 하지 않았다.

## 결론
- 모의 운용 시스템을 완성했다. 실시간 공개 시세를 받아 Phase 0과 같은 상태 기계로 가상 주문을 낸다.
- 테스트는 실거래 75개, 연구 19개로 모두 통과했다.
- 별도 리뷰어가 검토했다. 실주문이나 키 노출 경로는 없었고, look-ahead 문제도 없었다. 지적된 9건은 모두 고쳤다.

## 구성
| 기능 | 구현 |
|---|---|
| 시세 | Binance 공개 REST와 WebSocket(1분봉, 체결, 호가). 마감된 봉(`x=true`)만 쓴다. 빠진 봉은 판단 직전에 REST로 채운다 |
| 신호·집행 | Phase 0의 `snapshot`과 `MakerChaseExecutor`를 그대로 쓴다 |
| 가상 체결 | 실제 체결 테이프에서 지정가를 관통해야 체결된다(닿기만 해서는 안 된다). 대기열 위치는 체결에 쓰지 않고 진단용으로만 기록한다 |
| 리스크 | 일일 손실 한도, 종목별 명목금액, 총 레버리지, 데이터 지연(10초), 시계 오차(1초). 진입만 막고 청산은 막지 않는다 |
| 킬 스위치 | `python -m live_momentum.cli kill`. 대기 주문을 취소하고 포지션을 청산한 뒤 새 진입을 막는다 |
| 재시작 | 상태를 원자적으로 저장한다. 재시작하면 놓친 분을 봉 규칙으로 따라잡는다 |
| 일일 리포트 | 모의 결과를 같은 날의 두 백테스트와 비교한다(실시간 수신 봉 기준, 공개 아카이브 기준). 거래 단위 일치, maker 체결률, 시장가 체결 차이, 봉 차이를 본다 |
| 운영 | systemd 서비스와 타이머(일반 사용자 권한, 키 없음). 배포 절차는 `deploy/DEPLOY.md` |

## 리뷰에서 발견해 고친 문제
| 심각도 | 문제 | 조치 |
|---|---|---|
| 높음 | 재시작 직후 디스크의 상태 파일이 빈 상태로 덮어써졌다. 첫 판단 전에 다시 죽으면 다음 재시작이 처음부터 재생해 거래가 중복될 수 있었다 | 복원 직후 바로 저장한다. 두 번 연속 죽는 경우를 테스트로 추가했다 |
| 중간 | 펀딩비를 세션 종료 가격으로 계산했다. 백테스트는 정산 시각에 끝나는 봉의 종가를 쓴다 | 백테스트와 같은 가격을 쓰도록 바꾸고 테스트를 추가했다 |
| 중간 | 리포트의 모의 수익률은 펀딩을 포함하고, 백테스트 수익률은 포함하지 않았다 | 펀딩 전 모의 수익률을 따로 보여 주고, 표에 기준을 적었다 |
| 중간 | 세션 준비가 실패하면 예외가 로그에 남지 않았다. 또 매분 재시도하면서 REST를 반복 호출했다 | 이벤트 로그에 기록한다. 재시도 간격을 60초부터 늘린다(최대 15분) |
| 중간 | 기록 도중 프로세스가 죽어 마지막 줄이 잘리면 리포트가 실패했다 | 잘린 줄은 경고만 남기고 건너뛴다 |
| 중간 | summary.csv 갱신 코드가 불분명했다 | 정리했다 |
| 낮음 | 손상된 봉 파일 하나 때문에 시작이 실패할 수 있었다 | 그 파일을 건너뛰고 REST로 다시 채운다 |
| 낮음 | 비밀 필드 검사가 6단계 깊이까지만 확인했다 | 50단계까지 확인하고, 더 깊으면 기록을 거부한다 |
| 낮음 | 리포트가 이벤트 형식 변화에 약했다 | 없는 값은 비워 둔다 |

## 2차 독립 리뷰 (2026-11-23)
새 리뷰어가 같은 여섯 영역(런타임, 체결 모델, 리스크 한도, look-ahead, 보안, 테스트)을 다시 검토했다. 실주문 경로, 키 노출, look-ahead는 이번에도 없었다. 확인된 문제는 모두 고쳤다.

| 심각도 | 문제 | 조치 |
|---|---|---|
| 높음 | 세션 종료 처리(`end_session`)를 별도 스레드에서 돌렸다. 그동안 시세 콜백이 같은 상태를 바꿀 수 있었다(데이터 경쟁) | 펀딩비 REST 조회만 스레드에서 하고, 종료 처리는 이벤트 루프 스레드에서 한다 |
| 높음 | 세션 준비 중 REST가 403/451(지역 제한)을 받으면 일반 오류처럼 처리해 재시도했다 | 즉시 프로세스를 멈춘다(종료 코드 2). Windows 감시 스크립트도 이 코드에서는 재시작하지 않는다. 테스트를 추가했다 |
| 높음 | systemd 유닛에 `PYTHONPATH`가 없어 서버에서 import가 실패할 수 있었다 | 두 유닛에 추가했다 |
| 중간 | 열린 포지션의 가격이 NaN이면 총 레버리지 합계가 NaN이 되어 한도 검사를 그냥 통과했다 | 노출을 알 수 없으면 진입을 막는다(`unknown_exposure`). 테스트를 추가했다 |
| 중간 | 총 레버리지 계산에서 진입하려는 종목의 기존 노출을 뺐다 | 모든 종목의 노출을 합산한다 |
| 중간 | 호가가 오래됐을 때 시장가를 마지막 체결가로 채웠는데, 그 체결가가 오래됐는지는 확인하지 않았다 | 체결 출처를 `last_stale`로 표시해 리포트에서 구분한다 |
| 낮음 | 자산 파일이 없어지면 조용히 초기 자산으로 돌아갔다 | 경고 로그를 남긴다 |

체결 모델의 낙관성(대기열 위치 미반영)은 알려진 한계로 유지한다. 리포트의 대기열 진단으로 그 크기를 측정한다.

## 운용 시작 (2026-11-23)
- 사용자 결정에 따라 AWS 대신 현재 Windows PC(OpenStack VM, 4 vCPU, 16 GB)에서 운용한다. 절차는 `deploy/DEPLOY.md`의 Windows 절에 있다.
- 시계 오차는 Binance 서버 대비 약 0.1~0.2초로, 허용치 1초 안이다. 지역 제한도 없다.
- 사용자 결정(최소 단축안): 모의 5세션과 testnet 며칠을 거친 뒤, 결과 보고에 대한 사용자 승인을 받고 소액·총 레버리지 1배 이하로 실거래를 시작한다.
- 이번 주는 11/26 휴장, 11/27 조기 폐장(전략상 건너뜀)이 있다. 그래서 5세션은 11/23, 11/24, 11/25, 11/30, 12/1이다.

## 운용 전에 결정이 필요한 사항
1. **낙폭 축소 계산의 시작점.** Phase 0 보고서 §1에서 넘어온 문제다. 현재 구현은 2021-01부터 계산하고, 이 기준으로 지금 배율이 정상의 약 1/3이다(g=0.31). 모의 운용에서는 이대로 두고, 리포트로 영향을 본다.
2. **서버.** 배포 문서는 GitHub의 `feat/live-momentum` 브랜치를 서버에 clone한다. 그래서 배포 전에 이 브랜치를 푸시해야 한다.
3. **Phase 2로 넘어가는 기준(제안).** 최소 10세션, 2~4주 운용한 뒤 아래를 모두 만족해야 한다.
   - 실시간 수신 봉 기준 백테스트와 아카이브 기준 백테스트의 거래가 95% 이상 같다(데이터 경로 검증)
   - 모의 결과와 실시간 봉 기준 백테스트가 진입과 청산의 방향·시각에서 일치한다(집행 경로 검증)
   - 실제 테이프 기준 maker 체결률을 1분봉 규칙 기준 체결률과 비교해 보고한다. 이것이 핵심 측정 항목이다. 차이가 크면 백테스트 성과를 그 체결률로 다시 계산한 뒤 진행 여부를 정한다
   - 처리되지 않은 크래시가 없다. 재시작할 때마다 복원이 정상이다

## 알려진 한계
- 가상 체결은 대기열 위치를 반영하지 않으므로 낙관적이다. 앞에 있던 잔량은 기록하므로, 리포트에서 얼마나 낙관적인지 추정할 수 있다.
- 실주문 경로(Phase 2)는 구현하지 않았다.
